# Design overview

`vibrator` is an orchestration loop for repositories where Claude
(Anthropic, via the `claude` CLI) is the implementation worker. Its job
is not to replace project judgment; its job is to remove the
repetitive coordination work between intent, implementation, review,
fixup, description, and merge.

## Product thesis

Agentic coding gets interesting when a repository can keep moving
after a human has written the backlog. A single prompt to Claude can
produce a patch, but a useful software project needs an operating
system:

- choose the next safe item,
- respect dependencies,
- limit parallel work,
- run the implementation locally and open the resulting PR,
- run a review pass,
- route review feedback back to the implementer,
- detect conflicts,
- produce a reviewable final description,
- merge only when the loop is complete.

`vibrator` makes that operating system explicit and inspectable.

## Design goals

1. **GitHub-native control plane**: Issues, pull requests, review
   threads, checks, and merge state remain the primary coordination
   surface.
2. **Small local brain**: The orchestrator persists only session
   metadata needed to avoid duplicate work and understand the current
   phase of each item.
3. **Dependency-aware backlog flow**: Issue ordering starts with age
   (bugs first), then filters out blocked work using plain-English
   dependency phrases.
4. **Bounded autonomy**: `MAX_CONCURRENCY` prevents uncontrolled fan-out.
5. **Review-first completion**: Work is not done when a PR appears; it
   must pass a Claude-driven review pass and any required fix loop.
6. **Clean final merge artifact**: The final PR body and squash commit
   body are generated by Claude from the branch context and preserve
   closing references.

## Non-goals

- Replacing GitHub project management.
- Replacing human product direction.
- Inventing custom merge semantics outside GitHub's own controls.
- Maintaining a central server. `vibrator` is designed as a local or
  scheduled process that can be stopped and restarted.
- Inventing a custom workflow language. It intentionally leans on
  issue text, PR metadata, GitHub APIs, `gh`, `git`, and `claude`.

`vibrator` still treats GitHub as the merge authority. Its default path
is a normal squash merge after the review/fix loop is clean. If the `gh`
CLI reports that the merge is blocked specifically because the base
branch policy requires an administrator bypass, `vibrator` retries that
same squash merge with `--admin` rather than failing the loop outright.

## Architecture

```text
                ┌──────────────────────────────┐
                │          GitHub repo          │
                │ issues · PRs · reviews · CI   │
                └──────────────┬───────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                         vibrator                             │
│                                                              │
│  load snapshot  →  reconcile sessions  →  build plan         │
│        │                    │                 │              │
│        ▼                    ▼                 ▼              │
│  GitHubClient       FileSessionStore      orchestrator       │
│        │                    │                 │              │
│        └────────────────────┴─────────┬───────┘              │
│                                       ▼                      │
│                               execute actions                │
└───────────────────────────────────────┬──────────────────────┘
                                        │
                                        ▼
                                 ClaudeAgentClient
                          (runs `claude` CLI in a checkout,
                           implements / reviews / fixes,
                           commits + pushes the branch)
```

### Core modules

- `src/index.ts` parses configuration, prints operator-friendly
  status, loads snapshots, reconciles sessions, builds plans, and
  executes actions.
- `src/orchestrator.ts` contains the pure planning rules: dependency
  parsing, issue eligibility, PR phase selection, and final-body
  closing-reference logic.
- `src/actions.ts` translates planned actions into Claude-agent
  invocations and the corresponding GitHub API calls (open PR, post
  review, update body, squash-merge).
- `src/claude-agent.ts` is the local Claude coding-agent client. It
  clones / updates a checkout, runs the `claude` CLI with structured
  prompts, parses sentinel-marked output for structured payloads, and
  commits / pushes results.
- `src/github.ts` wraps the GitHub REST and GraphQL surface used by
  the loop (issues, PRs, reviews, review threads, status checks,
  workflow approvals, merges).
- `src/reconcile.ts` fails any leftover `in_progress` sessions at the
  start of every iteration — every Claude action runs synchronously,
  so an active session can only be a crashed-process carcass.
- `src/session-store.ts` persists session state in a local JSON file.
- `src/dashboard-server.ts` serves the real-time **Dashboard** at
  `http://localhost:3000`. The Dashboard includes Panel B (Issue → PR
  Lifecycle), live orchestrator logs, and a GitHub activity feed.
- `src/dashboard-utils.ts` provides event-emission helpers used by
  `index.ts` to push orchestrator state to Dashboard clients.

## Data model

The orchestrator works from a `RepositorySnapshot`:

- open issues,
- open pull requests (with conflict / check / review-state hints),
- locally persisted agent sessions.

An `AgentSession` records the phase, status, linked issue or PR,
timestamps, and small phase-specific result values such as the head
SHA observed after a fix push. This is enough to answer questions
like:

- Did Claude already implement this issue?
- Did the latest review leave inline comments?
- Did the PR head SHA change after fix instructions?
- Was a final description already generated?

## Planning model

Planning is deterministic:

1. Sort open issues and PRs by creation time.
2. Build a blocked-issue index from `blocked by`, `depends on`, and
   `blocks`.
3. Plan PR work first, because open PRs already consume repository
   attention.
4. Count active PRs plus in-flight implementation sessions.
5. Use remaining concurrency for the highest-priority eligible
   unblocked issues (bugs first, then oldest-first).

This keeps the system conservative. Existing work is shepherded
before new work starts.

## Action model

Planned actions are intentionally high level:

- `start-implementation` — Claude implements the issue in a local
  checkout and vibrator opens the PR.
- `review-pull-request` — Claude reviews the diff and vibrator posts
  the review (approve, or request-changes with inline comments).
- `address-review-comments` — Claude addresses every unresolved
  review comment, pushes fixes, and vibrator resolves the review
  threads.
- `address-failing-checks` — Claude inspects failing CI logs, fixes
  the underlying problems, and pushes.
- `resolve-conflicts` — Claude rebases the branch on the base branch
  and resolves any conflicts.
- `write-final-description` — Claude writes the final PR body from
  the branch's commits and diff; vibrator updates the PR body and
  squash-merges.

Each action is idempotence-aware through session state. A later
iteration can observe what changed and move to the next phase instead
of repeating the same work.

## Safety and operator control

- Use `--dry-run --once` to inspect the plan without mutating
  GitHub or running Claude.
- Keep `MAX_CONCURRENCY` low until the repository's issue quality
  and CI signal are trustworthy.
- Use branch protection and required checks as the final safety net.
- Keep issues small enough for agentic implementation and review.
- Use explicit dependency phrases when order matters.

## Why the final-description step matters

Agent-generated PRs often start with sparse or placeholder
descriptions. Before merge, `vibrator` asks the local `claude` CLI to
read the commits and diff on a checkout of the PR branch, and uses
the result as both the final PR body and squash commit body. Closing
references are preserved or appended so GitHub issue automation still
works.

That turns every merged unit into a useful historical artifact
instead of a trail of placeholder text.
